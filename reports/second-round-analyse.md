| 1 | Apache Flink engine + StreamPark or Dinky console | Flink is the core stateful stream engine. StreamPark manages packaged Flink jobs; Dinky supports Flink SQL authoring/debugging. Use Kubernetes for deployment and Flink metrics/Prometheus for runtime visibility. | Kafka/Redpanda for early PoC. RocketMQ final path through Flink RocketMQ source/sink connector. | Filter: strong via DataStream or SQL `WHERE`. Convert: strong JSON parse, projection, enrichment, schema conversion, serialization. External call: supported via async I/O operators for HTTP/gRPC; needs timeout, retry, circuit breaker, and backpressure controls. | Runtime SQL can be submitted through SQL client/Dinky. Java DataStream changes usually need JAR redeploy. StreamPark adds job lifecycle UI, restart controls, savepoint/checkpoint workflow, and cluster operations. | Best production-grade core for wallet-event correctness, replay, keyed state, windows, joins, and future stateful requirements. Strong Java fit and clear path from Kafka PoC to RocketMQ. | Operational complexity: checkpoint tuning, state backend sizing, connector version compatibility, and team learning curve. RocketMQ connector must be validated under target version and load. | Build one RocketMQ source/sink payment authorization pipeline with checkpointing, failure/restart test, duplicate-event test, async external-risk-call test, and latency/throughput measurement. |
| 2 | Apache SeaTunnel engine + config-managed jobs | SeaTunnel handles streaming ETL through declarative job configs. Use SeaTunnel Zeta engine first unless the team wants Flink runtime standardization. Store pipeline config in Git and deploy through Kubernetes jobs or controlled scheduler. | Direct RocketMQ source and sink for final path. Kafka/Redpanda remains acceptable for local PoC parity. | Filter: supported through SQL/config transforms. Convert: good JSON parse, projection, mapping, simple enrichment. External call: weak/default not ideal; validate HTTP/API lookup carefully or offload to another service/engine. | Runtime config is job-file driven. New pipelines are introduced by submitting configs; running logic generally changes by restarting/redeploying the job. | Strongest config-first option if the company wants ETL without writing Java code for every route. Direct RocketMQ source/sink support is a major fit advantage. | Connector behavior and delivery semantics need deeper testing. Complex business rules or external calls may push the team back to Flink or service code. | Run direct RocketMQ-to-RocketMQ stream job with JSON filter/enrich, malformed-message handling, restart test, and config promotion flow from Git. |
| 3 | Apache Camel on Spring Boot + Kubernetes service deployment | Each pipeline is a Spring Boot service containing Camel routes. Use Actuator, Micrometer, structured logs, retries, dead-letter topics, and standard CI/CD. Application teams can own pipelines like normal Java services. | Direct RocketMQ through Camel RocketMQ component. Kafka/JMS/Rabbit can be used for bridge or PoC scenarios if needed. | Filter: strong via route predicates/processors. Convert: strong JSON marshal/unmarshal, schema mapping, validation, Java enrichment. External call: strong for HTTP/gRPC/internal calls; use timeout, retry, bulkhead, and idempotency patterns. | Runtime config through Spring properties, route templates, feature flags, or controlled service redeploy. Not low-code, but very manageable for Java/Spring teams. | Best fit for current Java/Spring Boot stack and service ownership model. Lower platform risk than large ETL systems if pipelines are deterministic and not heavily stateful. | Less suitable for large stateful stream processing, event-time windows, large joins, and exactly-once-style streaming guarantees. Runtime self-service is weaker than NiFi/SCDF/StreamPipes. | Build a Spring Boot RocketMQ source/sink pipeline with route-level dead-letter handling, idempotency key test, gRPC enrichment call, timeout/retry behavior, and production-like observability. |
| 4 | RocketMQ-native stack: RocketMQ Streams + RocketMQ Connect + RocketMQ EventBridge | Use RocketMQ Streams for lightweight stream processing, RocketMQ Connect for data movement, and RocketMQ EventBridge for event routing/rule-based fan-out. Keep all components close to RocketMQ operational model. | Native RocketMQ end to end. Connect handles file/database movement; Streams handles event processing; EventBridge handles bus/rule/target delivery. | Filter: supported by Streams and EventBridge rules. Convert: Streams Java map/enrich; EventBridge JSONPATH-style reshape. External call: possible in Streams Java code; use cautiously with timeout, retry, and isolation controls. | Runtime config is mixed: EventBridge and Connect are REST/config driven; RocketMQ Streams is more code-first. Operationally coherent if the company standardizes on RocketMQ. | Best RocketMQ-native direction and avoids making Kafka/Flink mandatory core infrastructure. Good if wallet events need lightweight transformation/routing rather than deep stateful ETL. | Smaller communities and less mature ecosystem than Flink/Camel. Harder to cover advanced stateful ETL, exactly-once semantics, complex joins, and external-call governance. | Build one native RocketMQ path with Connect ingest, Streams transform, EventBridge fan-out, replay/failure test, and an optional Java external-risk-call processor. |
| 5 | Apache NiFi for controlled low-code flow management | NiFi acts as a visual/API-managed flow orchestrator. Use parameter contexts, versioned process groups, REST-created flows, provenance, backpressure controls, and governed promotion between environments. | Kafka/Redpanda is proven in the current PoC. RocketMQ path needs custom processor, JMS/HTTP bridge, or a deliberate adapter layer in the source/sink design. | Filter: strong via processors, scripts, record-path routing. Convert: strong JSON/record processors, schema conversion, enrichment, routing. External call: strong for HTTP via InvokeHTTP/scripts; gRPC needs custom processor/script/library validation. | Excellent runtime flow editing through UI/API. Versioned flows and parameter contexts support controlled promotion, but production governance is required to avoid uncontrolled edits. | Best option if business/ops users need visual pipeline management, provenance, and traceable flow behavior. Useful as ingestion/orchestration even if Flink/Camel handles core transforms. | RocketMQ source/sink gap is the main blocker. Script processors and external calls must be governed carefully for performance, security, and maintainability. | Validate RocketMQ consume/publish path first, then test parameterized flow promotion, backpressure, dead-letter handling, InvokeHTTP/gRPC-adapter enrichment, and multi-node behavior. |
